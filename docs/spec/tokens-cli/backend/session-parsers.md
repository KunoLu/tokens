# Session Parsers: One Parser Per Client

> `cli/tokens-core/src/sessions/` contains one parser module per supported AI
> coding client. Each parser converts that client's local session files into
> `UnifiedMessage`s. Adding support for a client means: a new parser module, a
> `ClientDef` registry entry, and a matching entry on the web side.

---

## The unified format

All parsers emit `UnifiedMessage` (`cli/tokens-core/src/sessions/mod.rs:63-93`):

```rust
pub struct UnifiedMessage {
    pub client: String,
    pub model_id: String,
    pub provider_id: String,
    pub session_id: String,
    pub workspace_key: Option<String>,
    pub timestamp: i64,
    pub date: String,
    pub tokens: TokenBreakdown,   // input / output / cacheRead / cacheWrite / reasoning
    pub cost: f64,
    pub cost_source: CostSource,  // camelCase serde: providerReported | estimated | unknown
    // … duration_ms, message_count, agent, dedup_key, session title
}
```

**Privacy boundary: totals only.** A parser extracts token counts, costs,
timestamps, and model ids. Message text is used transiently for estimation
(e.g. character counts in `sessions/kiro.rs`, `sessions/commandcode.rs`) and is
never stored in `UnifiedMessage` and never submitted — what leaves the machine
is aggregated per-day, per-model numbers (see
[Submit Pipeline](./submit-pipeline.md)). Do not add fields that carry prompt
or response content.

## The registry: `clients.rs`

`cli/tokens-core/src/clients.rs` is the single registry:

- `ClientId` — the enum of known clients (generated by macro, `clients.rs:136-139`).
- `ClientDef` — one static entry per client (`clients.rs:108-113`):
  `id`, `root: PathRoot`, `relative_path`, glob `pattern`, plus flags like
  `headless` / `parse_local`. Example: Roo Code scans
  `~/.config/Code/User/globalStorage/rooveterinaryinc.roo-cline/tasks` for
  `ui_messages.json` (`clients.rs:310-314`).
- `PathRoot` — where the client's data root lives: `Home`, `XdgData`,
  `Config`, `EnvVar { var, fallback_relative }`, or a self-contained resolver
  like `ReasonixHome` (`clients.rs:1-17`).

The CLI-facing `--client` enum (`ClientFilter` in
`cli/tokens-cli/src/main.rs:432+`) mirrors `ClientId` and converts into it —
the registry itself stays clap-free.

## Adding a new client

1. Create `cli/tokens-core/src/sessions/<client>.rs` and export it from
   `sessions/mod.rs`.
2. Return `UnifiedMessage`s; skip malformed records instead of failing the
   session (see `sessions/jcode.rs` lenient parsing).
3. Subtract cache overlap when the source's input count includes cache reads
   (`TokenBreakdown` stores non-cached input and cache hits separately — see
   `sessions/cline.rs:63-67`, `sessions/gemini.rs:464-467`).
4. Add the `ClientDef` row in `clients.rs` and the `ClientFilter` variant in
   `main.rs`.
5. Add the client id to `SUPPORTED_CLIENT_TYPES` in `web/src/lib/types.ts:1-46`
   — the server rejects unknown client ids.
6. Use `rusqlite` directly for SQLite-backed clients (e.g. OpenCode); there is
   no ORM layer in this workspace.

## Cache-inclusiveness rule

Several vendors report input tokens *including* cache hits. The convention is
to subtract the cached portion before storing, so `TokenBreakdown::total()`
never double-counts; each parser documents its source's accounting in a header
comment (existing examples: Cline, Gemini, Grok, Devin).
